## 1. The target shape — what "Fang-native" means (and the worked example)

Every port lands in the same five mechanics, because that is how everything in Fang already works:

- **A hand with a playbook** does the judging/composing (agents never enumerate; playbooks name exact keys).
- **kv record families** are the store (`contact/`, `formsub/`, `sms/`, `draft/`…), projected — never dumped — onto surfaces.
- **A deterministic sidecar** (pull-sync + sidecar-phases.py pattern) does all carrying: external HTTP, enumeration, verification, hashing. No model ever writes a deterministic record.
- **Cron workflows** schedule the sweeps; **Needs-you approvals** gate anything that leaves the studio.
- **A surface package** (own tile in the dock/drawer, own module dock) presents it, plain-language only.

**Worked example — Canvas (already done, all three hosts).** One self-contained package (`~/workspace/studio-design-plugin/`, manifest `plugin.json`: id `studio-design-generator`, ~70 declared ops, its own icon, a per-host expression written into the manifest itself). Its Fang expression, verbatim from the manifest's `hosts.openfang`: *"A Hand (same pattern as hands/forms and hands/surface-builder) plus a Studio surface; storage in Fang kv/memory under design/<id> and artist/<id>/ keys; approvals via Needs-you."* The landing (RESULTS17/18-FANG-OPS.md): the deterministic core runs as sidecar jobs behind an op allowlist (29 → 46 ops wired live), records live in `design/`, `designcover/`, `library/` families (the element library is rebuilt from kv each cycle), artist opt-in + approval ride `artist/<slug>` profiles and Needs-you, and the surface sits in the drawer's Studio family. **This morning's style-skill mechanism is the newest instance of the same pattern**: per-artist style knowledge as records — `style/<artist>/<name>` kv entries plus `style_presets` on the artist profile — consumed by the designer hand's playbook, no new code path. (The style records live on the live instance; they are not in the local tree this inventory read — existence per the commission, contents UNVERIFIED locally.)

**The meta-finding:** both donor systems independently evolved a package discipline Fang can adopt as its stated convention — StaxCloud's `app-manifest.js` capability declarations (curated, non-executable, "discovery never grants authority") + `staxbox.skill-package.v1` format (hashed file lists, compatibility verdicts), and InkStax's `app.toml` package loader (`crates/core/src/package.rs`: closed manifest field set, loader verifies manifest-named files exist, hashes manifest + resolved grant, **grants never come from the manifest's declarations**, packages may not shadow builtin tiles). Canvas's `plugin.json` already sits between the two. **Recommendation: adopt the Canvas manifest as Fang's plug-in package format, hardened with InkStax's two loader rules (verify + hash; grants resolved outside the manifest).** That is Row 0 below — it makes every other row cheaper.

### 3.3 What Fang needs to become the second consumer of the same app
Fang re-expresses the click-connect design in its own mechanics — the Rust code does not move; the *design* (which StaxCloud already proved out) does:

1. **Redirect URI.** Square's console registers **multiple redirect URLs per environment** (the console field is Redirect URL(s); multi-registration is in production use) — so Fang's finalize URL is **added, not substituted**: `https://fang.sefer.team/square/finalize`, Production + Sandbox, alongside the existing Dell one. The finalize door itself is served by a small Cloudflare Worker on the zone (the `fang-forms` pattern — Fang has no daemon route for this and needs none): it validates `state`, and hands the code to the sidecar through the KV queue/doorbell. Owner hand-step: the console edit (~2 min, same shape as the Oct 26 sitting).
2. **Custody — tokens never touch kv.** Fang's kv is agent-readable; OAuth tokens there would break the grounding/security posture. Custody follows the #150 shape, translated: a **sidecar-only custody file (0600)** in the sidecar's own directory (the pull-secret precedent) holding access/refresh tokens, merchant_id, location_id, and the webhook signature key. kv carries only a projection — `square/status` {connected, environment, location name, merchant display, last event, updated} — which Connections and Boards read. The lead's playbook can say "Square is connected to Fargo Tattoo" from the projection and can never see a token.
3. **Connect flow in Fang terms.** Connections surface → "Connect Square" → Square-hosted consent (scopes = the lane-a widened set, so the fee scope is held from day one and no reauthorization is ever needed — the exact lesson #150 encoded) → finalize Worker → sidecar exchanges the code, fetches `/v2/locations`, and the owner picks **Fargo Tattoo** from the pick-list in the same surface → sidecar calls `ensure`-style registration (below) → status projection flips to connected, read back before anyone claims it (playbook rules 13/14 apply).
4. **Programmatic webhook registration.** Reuse the #150 mechanism as a sidecar phase: with the app's personal access token (held as a Worker secret / sidecar custody — see hand-steps), list subscriptions → create-or-update Fang's own `"StaxCloud deposits — fang.sefer.team"` with the same 8 events at API 2026-01-22 → capture the signature key at create/rotate into custody. Events are delivered by Square to a **webhook door Worker** (fang-forms pattern again): it verifies HMAC-SHA256 over `notification_url + raw_body` with the custody key (Worker secret copy), enqueues verified events to the zone KV, and pull-sync's doorbell carries them to the sidecar, which applies them to kv families — payments/refunds to `deposit/` + the linked `project/`/contact records (the `apply_scoped_payment` rules from main's receiver, re-expressed), and **`booking.created/updated` to `booking/` records — a handler StaxCloud never wrote; Fang gets booking truth from webhooks for the cost of one match arm**, with the availability law intact (bookings are records; availability is still never *stated* — the booking link remains the customer-facing answer).
5. **Refresh discipline.** Code-flow refresh tokens are multi-use and do not expire unless revoked; the response returns the same refresh token. Sidecar refreshes on a weekly cadence (Square's guidance), a failed refresh raises Needs-you immediately — well inside the 15-day post-expiry grace — instead of failing silently at expiry.
6. **One merchant, two grants — the transition answer.** *Each system holds its own grant; one shared connection is neither needed nor recommended.* Square's own reference presupposes multiple live access tokens per account per application ("If an account has more than one OAuth access token for your application, this endpoint revokes all of them") — concurrent grants are a supported shape, and the Dell's production connection is untouched by Fang connecting. Copying the Dell's grant to Sarah's box would technically work but couples custody, rotation, and revocation across the two systems during exactly the window Fang must prove itself independently. **Standing caution for both systems during transition: nobody calls revoke** — a plain `/oauth2/revoke` kills *all* tokens for the account+app (single-token revocation requires `revoke_only_access_token: true`), and a merchant-side revoke in Square's dashboard does the same. Detection is covered without an extra event: Fang learns of revocation at its next refresh/API call and surfaces it as Needs-you (the 8-event deposits set deliberately excludes `oauth.authorization.revoked`; adding it is a one-line option if the owner wants belt-and-braces).
7. **What Fang does NOT need from Square:** deposits charging (StaxCloud's Web Payments SDK guest-deposit flow is a StaxCloud surface; Fang's deposit story is webhook-observed state + the existing booking link), card vaulting (`v046` internals UNVERIFIED; Fang holds no card data), customers sync (doesn't exist), appointments sync (doesn't exist — webhooks + the owner-directed public booking page are Fang's booking inputs).

**Class RE-EXPRESS, effort M–L** (the doors are proven patterns; custody, registration, refresh, and the sandbox-then-production proof are the work). **Slot: NEW "Square" slot after Round C** (contacts/projects must exist for deposits and bookings to land on), sandbox connect proof first, production connect as the gate. **Owner hand-steps:** (a) add Fang's redirect URL in the Square console, Production + Sandbox (~2 min); (b) the in-product Connect click + location pick when the surface ships (~2 min, by design — this is the click-connect UX working as intended); (c) platform credentials (app secret + personal access token) enter Fang's custody via the Secure Vault capture route — Stax places them as Worker secrets + the sidecar custody file; values never transit chat or kv.

## 4. EMAIL — the StaxCloud wiring as it stands, and Fang's version of it

**As it stands (repo + verified project record).** `staxos/kernel/src/api/email_adapter.rs` (843 LOC) defines a provider seam (`trait EmailProvider`: send / verify_webhook / parse_inbound); the adapter owns no inbox/approval state. Cloudflare is the live provider; Resend is dormant behind the same seam. The **entire outbound Cloudflare surface is one API call**: `POST /accounts/{account_id}/email/sending/send` with `{from, to, subject, text, headers:{In-Reply-To, References}}` — threading headers preserved, exactly-once keyed on RFC Message-ID. Inbound: Cloudflare Email Routing → the relay Worker **`staxos-email-relay`** (`staxos/cloudflare/email-relay-worker/worker.js`, 130 LOC; parses with postal-mime, preserves `In-Reply-To`/`References`, routes on the *envelope* recipient) → POSTs normalized JSON to the instance webhook `POST /api/webhooks/email/inbound`, verified by HMAC-SHA256 over `{timestamp}.{body}` with a shared secret (300 s tolerance, constant-time compare) before parsing. Held drafts are reviewed through the same draft+approve discipline as SMS (cs-email review routes); mailboxes are gated by an `email_mailboxes` registry — unregistered addresses admit nothing. Verified live posture: account `e3304f1e4edd51e58650c7efcb0c09bc`, **Workers Paid active**, sending domain `staxcloud.ai` onboarded (cf-bounce MX ×3, DKIM, SPF, DMARC p=reject); HQ mailbox `support@staxcloud.ai`. The relay Worker is deployed **unbound** — the routing-rule flip is a separate step by design.

**The known blocker, precisely.** The cloud instance's stall was never the API call — it is *placing a token value into a host's environment*: the owner's Cloudflare user token lacks the API Tokens permission, so no agent route can mint the dedicated `StaxOS email sending - …` token, and Cloudflare never re-displays an existing token's value to copy. Any Fang design that needs a Cloudflare token **on Sarah's box** inherits that exact blocker.

**What Fang needs instead (assessed against what Fang already has).** Fang's zone/workers estate is already live (`fang-forms`, `fang-web`, `fang-assetlinks` Workers; zone `sefer.team`; tunnel `fang.sefer.team`). The Fang-native expression keeps every credential inside Cloudflare and puts only a mintable-by-us secret on the box — the HMAC pattern Fang already runs for pull-sync:

- **Inbound (WRAP-adjacent):** `staxos-email-relay` is instance-parameterized by design (`INSTANCE_WEBHOOK_URL`, `RELAY_SECRET`, `FALLBACK_DESTINATION` bindings). A Fang binding of the same Worker points at a Fang door (a small intake Worker or the tunnel) whose sidecar verifies the same HMAC shape, then writes `email/<thread-id>` + `emailmsg/…` kv families mirroring `sms/` exactly. An **email hand** (sibling of the sms hand, same playbook skeleton) drafts; drafts ride Needs-you; the mailbox registry becomes a kv allowlist record the sidecar checks before admitting anything.
- **Outbound (the blocker dodge):** sends are performed **by a Worker** calling the one Cloudflare send API with the account credential held as a Worker secret — the box never holds a Cloudflare token. The sidecar hands the Worker an approved, exact message (recipient + body from the approved `smsout`-shaped record family, `emailout/<uuid>`) over an HMAC-signed call; the Worker sends and returns the receipt; the sidecar stamps delivery read-back. This is a design choice to confirm at build time (the existing relay Worker is inbound-only today), but it is the only route that makes Fang email **independent of the token-placement blocker** — and it reuses the adapter's one-call surface unchanged.
- **Domain/mailbox:** the pattern ports 1:1; *which* mailbox/domain Fang serves first is a product decision, not a wiring problem (sending domain onboarding is the same Cloudflare flow already proven on staxcloud.ai; fargotattoo.com mail stays on Google Workspace per standing record — Fang CS email would start on the product domain, exactly as cloud V1 plans: website customer service + email, Cloudflare both directions, no Resend ever).

**Class RE-EXPRESS, effort M** (Worker doors + sidecar intake exist as patterns; the email hand is a playbook clone of the sms hand). **Slot: NEW "Email" slot after Round D** (Connections must tell the truth about it — Round D's projection work is the natural carrier). **Owner hand-steps: none on the recommended route** (the API-Tokens permission row is needed only if a box-resident token is ever chosen — explicitly avoided).

## 6. TEAM-CHAT CHANNELS — the "teams" correction (distinct from SMS)

**What StaxCloud actually has (repo-verified): a genuine internal team chat — and zero external team-chat integration.** Negative evidence: `slack|microsoft teams|discord` across kernel/web/docs hits only a secret-shape regex and a design-research link. There is no Slack/Teams/Discord/Buzz connector, webhook, or API client to port.

**The internal system — Team Workspace (`staxos/kernel/src/api/team_workspace.rs`, 4,720 LOC):**
- A **Team is an artist row** (`team_channels.team_id REFERENCES artists(id)`). Membership is implicit — every active user of the subscription who belongs to that artist (or is owner) is a member; there is **no per-channel membership table**, no private channels in practice.
- Channels: exactly one auto-created per Team — **`Work` (`kind='work'`)**; the schema permits `kind='custom'` but **no create-channel route exists** (custom channels are schema-permitted, effectively unused — UNVERIFIED beyond the route search).
- Messages: `team_messages(…, actor_type ∈ human|bot|system, actor_id, message_kind ∈ text|bot|work|system, object_type/object_id)` — one stream where humans, bots, and system notices (e.g. line-watchdog posts) appear as named participants; every message also emits a `team.message.created` business event; human posts push-alert teammates.
- **The agent's seat is a bot installation, not a user account:** `team_bot_installations` installed from a frozen template catalog of exactly two — `artist-assistant.v1` (tools incl. search_clients, add_client_note, propose_form_revision, calendar_*) and `help-desk.v1` (tools incl. list_sms_threads, draft_sms_reply, recall, request_teammate_answer) — each with `tools_json`, `knowledge_scope` (prose), `triggers_json`, `model_policy`, `budget_cents`, **`approval_policy`**, and state active|paused|removed. The workspace read resolves bot display names into the transcript alongside humans.
- **@mentions are declarative only:** both templates list the trigger string `"direct Team mention"`, but **no mention parser exists** in the channel code (NOT FOUND) — a port must not assume `@bot` syntax is parsed.
- **The handoff loop is real:** `communication_handoff.rs` — a bot asks a *named teammate* a question (`request_teammate_answer`); the human's answer lands as a `team_messages` row and wakes the conversation, producing a **held draft, never a send**.

The port: kv families `channel/<artist-slug>/<channel-slug>` + `channelmsg/<channel-slug>/<id>` (actor = owner | stax | system, mirroring `team_messages`' actor model); membership = the soft artist scoping the owner already ruled (Team = artist; owner sees across); the two StaxCloud templates become **playbook postures of the one lead** (One Face law: the channel shows Stax, never a roster of bots — artist-assistant/help-desk behaviors are things Stax *does* in the channel, behind the same playbook rules 1–14); StaxCloud's `approval_policy` per bot maps to Fang's existing rails (drafts → Needs-you; scripted replies per the owner's ruling); `request_teammate_answer` re-expresses as `handoff/<id>` records + a Needs-you card ("Leni — a customer asked X; your call?"), with her answer waking the thread — the handoff semantics port whole.
