## A. BOARDS

### A.1 What a board mechanically is — SOURCE

- A board is **one kv record**: key `surface/<slug>`, value JSON `{"title": "…", "blocks": [ … ]}`. (hands/surface-builder/HAND.toml, system prompt "HOW SURFACES WORK"; SKILL.md "Compose".)
- **Who writes it:** the Surface Builder hand's agent, in conversation, using only `memory_store` / `memory_recall` (HAND.toml tools list). The owner asks in chat; the agent composes blocks and stores the record in the same turn. Other crew agents can write `surface/` records the same way — the Canvas board's content (below) was composed into a record during the Canvas landing, not authored in any file in this repo (grep for its strings across the fork workspace finds them in no source file).
- **Block schema v1** (HAND.toml): `heading {text}`, `text {text}`, `stats {items:[{label, value}]}`, `list {title, items:[{title, sub?, badge?}]}`, `kvlist {title, prefix}` — a kvlist renders live memory rows under a key prefix. Unknown block types degrade to a "newer block" note.
- **Delete:** storing `{"deleted": true}` tombstones it (renderer hides it); the Boards page's Delete button does a real REST DELETE (SKILL.md "Remove").
- **Renderer:** `boardsPage()` in `crates/openfang-api/static/js/app.js` + the "Page: Boards (R6 surfaces engine)" template in `index_body.html`. It loads the whole kv snapshot, filters `surface/*` non-tombstones for the list, and renders the selected board's blocks verbatim.

### A.2 Why the Canvas board looks the way it does — SOURCE, three separate defects

The owner's screenshot (Boards → Canvas) shows a raw `{"designs":[]}` dump, GATE/RULE badges, and a stat card reading "see list below". Each has a distinct mechanical cause:

1. **The raw JSON dump is the kvlist renderer's fallback.** `kvRows()` in app.js builds each row's summary as `v.title || v.status || v.name`; when a record has none of those fields it falls back to `sub = JSON.stringify(v).slice(0, 90)`. The design index record under the board's prefix is `{"designs":[]}` — no title, status, or name — so the renderer prints the raw JSON as the row text, with the key remainder ("index") as the row title. Any kv record without a human summary field will dump raw JSON onto an owner surface through this path.
2. **The GATE/RULE badges are literal strings in the board record, printed verbatim.** The list-block template renders `x-text="it.badge"` with no vocabulary constraint. The Canvas board's "HOW IT WORKS" list items ("Artist approval first", "Customer designs are opt-in", "Transparent, layered, always") carry badge values `GATE` / `GATE` / `RULE` — the design product's internal policy vocabulary, composed into owner-facing content when the board was written. The renderer has no rule that keeps engine/policy words off the surface.
3. **"see list below" is a placeholder stored where a number belonged.** The stats template renders `it.value` as the big headline text verbatim. The Canvas board's stats items are `{value: "see list below", label: "Designs stored"}` and `{value: "Needs-you queue", label: "Approvals waiting"}` — the first is a pointer, not a count; the second puts a queue *name* in the number's place. The record was composed without the real counts ever being filled in.
4. A fourth, smaller one from the board **list** (owner screenshot): each board card shows "**5 blocks**" — the template prints `s.blocks.length + ' blocks'`, a structural count that tells the owner nothing about the board's content or freshness.

Contrast (**SOURCE**): the SEO board — the R6 thesis proof — follows the hand's own honesty rules (stats marked "not measured yet" instead of invented, a "Working on" list with queued/doing/done badges, a "Checks" list; LOOP.md R6 entry). The hand's playbook already states the standard the Canvas board violates: *"A board an owner cannot read in 20 seconds is a failed board"* and *"never fabricate rankings, counts, or results"* (HAND.toml). The Canvas board is a content failure against existing rules, amplified by two renderer failures (the JSON fallback and the unconstrained badge/stat rendering).

### A.3 The product answer — PROPOSAL

**One owner sentence:** *Boards are live dashboards your team keeps for you — each one answers "how is this part of the shop doing, and what needs doing next" at a glance.*

That is what the machinery already is: an agent-maintained, record-projected page per workstream. The owner's guess ("dashboards of some sort") is right; what failed is that nothing enforced dashboard discipline on the content or the rendering.

**Glance-bar rendering rules (proposed as build law for the Boards slice):**

1. A stats value is a number or a short state ("3", "None waiting"). A sentence or placeholder in a stat slot renders as text, never as the headline — and the surface-builder playbook is forbidden from storing one.
2. A kvlist row must render a human summary (title/name/status). A record with no summary renders as a **count line** ("3 designs stored"), never as raw JSON. Raw JSON on an owner surface is a build failure, full stop.
3. Badges come from a closed plain-words set — **Waiting · Doing · Done · Needs you**. Anything else (GATE, RULE, or any policy/kernel word) is mapped or dropped at render time, and the playbook stops writing them.
4. Every board ends with a **Next actions** list: named action, named owner ("Reply to the newest review — Stax has a draft waiting").
5. Board list cards show the board's headline number and freshness ("Designs — 4 stored · updated 2h ago"), never a block count.
6. Empty states say what the board *will* show ("No designs yet — new designs land here"), not that nothing is stored.

**Three concrete Fargo Tattoo boards under those rules:**

1. **Fargo Tattoo SEO** (exists; the model citizen). Stats: Google rating *(only once actually measured — until then the slot honestly reads "not measured yet")*, Reviews waiting for a reply (real count), Photos current (Yes/Needs refresh). Next actions: "Reply to this week's review — draft waiting in Work." Checks list as today.
2. **Designs** (the Canvas board, fixed as an interim). Stats: Designs stored (the real count of design records), Waiting your OK (real count). List: the latest designs by title with status badges (Waiting your OK / Approved / Sent to client) — composed from the design records' own title/status fields, never a kvlist dump. This board **exits Boards** when the Canvas app surface ships (already a planned slice): the dashboard becomes Canvas's front screen, where it belongs.
3. **Saturday Walk-ins** (new; matches the shop's real rhythm — Leni's walk-in Saturdays). Stats: Walk-in inquiries this week (counted from text threads + form submissions), Artists on Saturday (Shawn / Leni), Days until Saturday. Next actions: "Post the walk-in announcement — draft waiting," "Confirm Leni's sheet is current." Every number is a count of records Fang already holds.

**The fold option, honestly evaluated:** folding Boards into **Work** mixes two different jobs — Work is a decision queue (Needs you / Current work / Finished); a dashboard is status you glance at, not a decision you make. Folding into **Studio** buries dashboards inside a drawer family and loses the dock-level glance; it also misfits, because a board is cross-cutting (the Walk-ins board summarizes Texts + Forms + people) and no single Studio app owns it. **Recommendation: keep Boards as the dock tab, redefined as agent-kept dashboards under the six glance rules; the Canvas board migrates out to the Canvas surface when that slice lands.** Boards earn their tab the day every board on the list can be understood in five seconds.

### B.2 What the research says — SOURCE (web, cited)

- **Few stages, each with entry/exit rules and a next action.** Small-business pipeline guides converge on the same spine — New inquiry → Contacted → Qualified → Next step scheduled → Proposal/quote sent → Won / Lost — and stress that the stage *rules* matter more than the names: every opportunity carries a stage, an owner, a next action, and an outcome, and two people should place the same lead in the same stage. Sources: [Kinetic — Small Business Sales Pipeline](https://usekineticai.com/blog/small-business-sales-pipeline); [Clozer — CRM Setup for Small Businesses](https://www.clozer.me/blog/crm-setup-small-business-dubai); [Nuru — CRM vs spreadsheet for small business leads](https://nurudigitalmarketing.com/blog/crm-vs-spreadsheet-small-business-leads).
- **Stages should mirror the business's actual sales process**, not a generic template ([GoHighLevel pipeline training notes](https://www.julianmills.co.uk/highlevel-training-workshop-free-live-sales-pipelines-opportunities/)); B2B-flavored stages (Negotiation, Proposal) shrink for an appointment business.
- **Speed is the biggest controllable factor.** The Lead Response Management study (Oldroyd / InsideSales, 2007; popularized by HBR, 2011): a web lead contacted within **5 minutes** vs 30 minutes shows ~100× the contact odds and ~21× the qualification odds. Treat the famous "78% of buyers purchase from the first responder" as **folklore — it has no traceable primary source** ([Expertise.ai — Speed-to-Lead Statistics, verified vs debunked](https://www.expertise.ai/stats/speed-to-lead-statistics)). For an agent-run shop this is the strongest argument in the set: Stax can answer in minutes at 9pm; a human with a tattoo machine in hand cannot.
- **Classification is worthless unless it forces an action.** Hot/warm/cold tiers must each map to a concrete follow-up: hot → personal outreach inside the hour; warm → nurture plus a scheduled check-in; cold → one helpful touch, then rest. "A score without a response plan is a vanity metric" ([small-biz lead scoring guide](https://dev.to/james_pinder_3e5813b28ad5/how-to-build-a-lead-scoring-model-small-biz-guide-3m5e); routing table in [Toolient — WhatsApp Lead Qualification Flow](https://www.toolient.com/2026/01/whatsapp-lead-qualification-flow-n8n-us-small-business.html)).

### B.3 The Leads surface for Fargo Tattoo — PROPOSAL

**Definition:** Leads = *people who asked about getting tattooed and haven't booked yet*, shown as a pipeline — where each person stands, who they're waiting on, and what happens next. Contacts (the address book) stays in Studio; a booked-and-finished person graduates to Contacts history.

**Stages** (shop words; five columns is the phone-honest maximum):

1. **New** — came in by form or first text; nobody has replied yet. *Exit:* first reply sent.
2. **Talking** — conversation under way. The card says who wrote last and who it's waiting on.
3. **Waiting on an artist** — the next step is an artist's call: an estimate to OK, a design to approve, a big-piece consult. (The same records surface in Work's Needs-you — Needs-you is the decision queue, Leads is the person's place; two projections of one record, which is the standing Verdict #2 pattern, not duplication.)
4. **Booked** — appointment set. *Exit:* appointment day passes → graduates to Contacts; no-show → back to Talking with a follow-up next action.
5. **Resting** — went quiet 7+ days, or "not yet." One gentle follow-up gets drafted; after that, they rest until they write again. Plus a quiet terminal state, **Not a fit**, for polite declines (out of scope, wrong artist) — recorded, never nagged.

**Temperature badge** (classification that forces action, per §B.2): **Ready** (asked for a time, a price next step, or sent references + a date — the artist sees it today, via Needs-you) · **Interested** (talking, no next step yet — Stax keeps it warm with the scripted replies) · **Just looking** (vague or someday — one helpful answer + the booking link, then Resting). No numeric scores anywhere; the badge is a word the owner already uses.

**One lead card shows:** name · the piece in their words ("dagger & rose cover-up, forearm") · artist (Shawn / Leni / not yet assigned) · last contact ("Text · 2h ago · waiting on us") · the next action as one plain line ("Send the booking link" / "Shawn: OK the estimate" / "Check back Thursday") · the temperature badge.

**Counts:** a stats strip at the top — New 2 · Talking 5 · Waiting 1 · Booked 3 — real counts of the records in each stage. Stage sections as accordions, the pattern the owner already approved on Work. A small segmented filter (All · Shawn · Leni) sits on the pipeline view, because "whose is it" is this shop's real routing question.

**Birth and movement, on existing machinery only:** a form submission (the Forms sweep already creates/resolves the contact) or a first inbound text on the shop line (the bridge's `attention/sms` index already names unanswered threads) creates the lead in **New**, source named, deduplicated against the contact index — an existing customer re-opens as a lead, never duplicates. Movement is proposed by the crew from real records (reply sent → Talking; booking seen → Booked; 7 quiet days → Resting) and the scripted moves apply themselves; anything that commits the shop (an estimate, a design send) stays a Needs-you approval, per the standing rails. The owner can also just tell Stax "move Marta to Booked" in conversation. No kanban drag-and-drop — on a phone, sections + agent moves are the honest primitive. The lead's state is a few fields (stage, temperature, next action, artist) written onto the existing contact record by the sweeps that already touch it — a projection, not a new store.

**Cleanup owed with the build:** the test records on the owner's surface today (the invented "John Doe" contact from the R7-era fabrication incident, the Marta/Riley/Wanda test contacts, and the R12 zombie-draft test thread in Texts) are test debris; the Leads build should keep test-flagged records out of owner surfaces by default, the same rule Submissions already applies with its "test" badge — here they should simply not render as people.

## D. FORMS — THE INKSTAX BLOCK BUILDER, SPECIFIED

### D.1 Fang Forms today — SOURCE

- A form definition is a kv record `form/<slug>`: `{title, fields: [{key, label, type, required, options?}]}` with exactly five field types — **text, email, phone, textarea, select** (R7-FORMS-PLAN.md; the Preview template in `index_body.html` renders exactly those five).
- The page's module dock: **Agent · My Forms · Submissions · Preview · Done**. My Forms shows read-only cards (title, "N fields – M submission(s)", Public form link, Preview/Submissions buttons). Submissions renders the submission records. Preview renders a def and files a test submission.
- **There is no owner-facing builder at all.** `js/pages/forms.js` contains `loadData`, lookups, and `submitPreview` — no create, no edit, no save of a definition. Forms are authored exclusively by the Forms agent writing kv defs from conversation. From the owner's seat, his verdict is accurate: he can look at forms, but he cannot build or change one with his hands. (Note on sources: two filenames from an early search — `apps/forms/docs/FORM-BUILDER-UX.md` under `inkstax-dev` — did not exist on disk when read back; they are **not** used as sources anywhere in this section. The InkStax material below is read from the shipped code in `TattooStax/ink-stax`.)

### D.2 The InkStax block engine — SOURCE (TattooStax/ink-stax, apps/shell/src + crates/core/src)

- **The document model:** a form (an "artifact") is a revisioned document `{blocks: […], revision}`; each block is `{id, kind, label, value, required, config}` (`business-studio-controller.mjs`; document store `crates/core/src/artifacts.rs`).
- **The catalog:** `crates/core/src/studio_catalog.json` defines **77 block kinds** across four families (Forms, Sites, Docs, Artifacts). The **Forms family has 43 kinds in six categories**: Fields (10: name, short/long text, email, phone, website, number, file upload, hidden, date…), Selection (6: choice, image choice, dropdown, number scale, star rating, thumbs), Consent (13: consent checkbox, client info, medical history, legal consent, touch-up policy, initials, signature, medical disclosure, minor+parent, photo/video release, aftercare…), Tattoo (7: tattoo description, reference images, deposit agreement, aftercare checklist, age verification, previous tattoos, allergy), Structure (3: section heading, instruction text, divider), Connected (4: appointment picker, booking gate, customer service…). Each kind maps to a **renderer**.
- **The canvas is the form itself** (`StudioBlock.svelte`): in editing mode every block renders as its *real control* — the actual textarea, dropdown, radio set, rating — with answering disabled and the label/default editable in place (`onEdit(block, key, value)`; editable keys are label, value, required). You edit the thing, not a settings table about the thing.
- **Adding:** a block **picker sheet** grouped by the catalog's categories, with search; it opens at an **insertion point** — after the currently selected block, or at the end — and the add operation inserts `{type:'add', id, kind, label, after}` and selects the new block (`openPicker` / `addBlock` in the controller).
- **Operations:** add / remove / **move** / rename / design / edit-block / configure-group / configure-choices / configure-range — all revision-checked mutations against the document. Choices are configured as **one option per line** of plain text; ranges by min/max; **group blocks are composites** (e.g. Medical History, Client Info) whose inner fields each carry enabled/label/required/options toggles — a whole consent section drops in as one block.
- **Why it feels clean (the owner's "at least the block engine"):** one visual catalog, insertion where you're looking, inline edits on the real control, composite blocks for the long legal sections, and no separate "form settings" world to learn.

### D.3 The Fang Forms spec — PROPOSAL

**Keep the spine, change the shape.** The def stays a kv record at `form/<slug>` (the Forms agent, the public Cloudflare form, pull-sync, and Submissions all already speak it). The `fields[]` entries grow into **blocks**: `{id, kind, label, required, config?}`. The five existing types map 1:1 onto kinds (text → Short Text, email → Email, phone → Phone, textarea → Long Text, select → Dropdown), so the live "Say hello" form and every agent-made form render unchanged. This is a superset of the current shape, not a new store and not a port of InkStax's artifact server — Fang keeps its kv spine, per the wiring law.

**Where Build lives:** the module dock does **not** change (Agent · My Forms · Submissions · Preview · Done). My Forms gains a **"+ New form"** action and an **Edit** button on each form card; both open the **Build view** for that form. The builder is one level in from the dock, where a tool belongs — and the agent path stays the front door (the standing agent-first law: most forms will still be born from "Stax, make me a consent form"; Build is for when he wants his own hands on it).

**The Build canvas on a phone (390px):** the form rendered as itself, blocks stacked full-width, exactly as Preview renders them today but in edit mode. Tap a block → it selects (outline) with a compact toolbar: **↑ · ↓ · Edit · ✕**. **Edit** opens that block's inline editor in a bottom sheet: label (text field), Required (toggle), and the kind's configuration — options one-per-line for Dropdown/Choice, min/max for a scale. A **"+ Add block"** button sits at the end of the canvas and between blocks on the selected block's toolbar; it opens the picker as a bottom sheet: category groups (Fields · Selection · Consent · Tattoo · Structure) with a search field, one tap inserts after the selected block and selects the new one. Save is explicit and honest: **Save form** writes the def (PUT `form/<slug>`), with the same record the agent reads — owner edits and agent edits are the same document, never two copies.

**The Fang catalog (v1)** — only kinds Fang's renderer can actually carry on both Build and the public form (InkStax's own discipline: a kind with no renderer shows as unavailable; Fang's v1 simply doesn't list those):

| Category | Blocks (kind → what renders) | Maps from InkStax |
|---|---|---|
| Fields | Short Text, Long Text, Email, Phone, Number, Date | Fields |
| Selection | Dropdown, Choice (radio set), Star Rating, Thumbs, Number Scale | Selection |
| Structure | Section Heading, Instruction Text, Divider | Structure |
| Tattoo | Tattoo Description, Previous Tattoos, Allergy note | Tattoo (text-carried kinds) |
| Consent | Consent Checkbox, Photo Release (checkbox + text), Aftercare acknowledgment | Consent (text-carried kinds) |

Deferred until the public renderer carries them (named, not silently dropped): File Upload / Reference Images (needs the public upload leg), Signature / Initials (needs a signature control), the composite group blocks (Medical History, Client Info — v2, once per-field toggles are worth it), and the Connected blocks (Appointment Picker — Square owns booking; the booking *link* is a Structure text block today).

**Primitive mapping, 1:1:** artifact document ↔ form def record · block ↔ field entry · catalog kind → renderer switch ↔ the Preview template's type switch, extended per kind · picker sheet at an insertion point ↔ Add-block bottom sheet · inline label/required edit ↔ the Edit sheet · configure-choices (one per line) ↔ identical · move operation ↔ the ↑/↓ toolbar buttons (phone-honest reorder; no drag handles at 390px) · revision-checked save ↔ Save writes the whole def back, the same whole-record write the Surface Builder playbook already uses for boards.

**What does not change:** Submissions, the public form's URL and intake contract, the asleep-test pipeline, the Forms hand's sweep, and Needs-you draft flow. The Forms hand's playbook learns the block shape so agent-composed forms arrive as blocks the owner can then adjust by hand — one record, two authors, no translation layer.
